## Initial source-backed authority map

This is an incomplete map of the current `mongoose` worktree, not a set of vulnerabilities or a complete permission proof.

- Object privilege/state flags are bit positions in `db_object_flag`: user, programmer, wizard, read, write, fertile, and additional anonymous/lifecycle flags (`src/include/db.h:252-279`). `is_wizard`, `is_programmer`, and `is_user` test validity plus the corresponding flag (`src/db_objects.cc:1315-1331`).
- The shared object permission helper allows an operation when the running programmer is a wizard, owns the object, or the object has the requested flag (`src/db_objects.cc:1307-1313`; contract in `src/include/db.h:289-296`). Individual builtins add their own checks, so this helper is not the whole policy.
- Programmed verb lookup requires the verb's x bit (`src/db_verbs.cc:229-237`, `src/db_verbs.cc:485-545`; contract at `src/include/db.h:581-589`). Parsed command lookup matches name and argument specifications without checking that bit (`src/db_verbs.cc:304-345`), and command execution then runs as the matched verb's owner (`src/tasks.cc:751-767`, `src/tasks.cc:811-856`, `src/execute.cc:3340-3372`). Therefore command verbs and callable verbs have different exposure rules; x-less wizard-owned command verbs remain in scope.
- Every successful `call_verb2()` activation takes its `progr` from the called verb's owner, not from the connected player or the caller (`src/execute.cc:663-740`). Command tasks likewise start with `RUN_ACTIV.progr = db_verb_owner(vh)` (`src/execute.cc:3340-3372`). Server-program tasks accept an explicit `progr` (`src/execute.cc:3291-3337`; ordinary server tasks pass the verb owner at `src/tasks.cc:1846-1861`). This makes verb ownership and callable wizard-owned verbs central to the audit.
- Nested calls set MOO `caller` from the previous activation's `this`; this is distinct from `caller_perms()`, which reads the previous activation's `progr` (`src/execute.cc:752-754`, `src/execute.cc:3721-3730`). The new activation normally inherits the previous activation's `player`; a wizard-permission caller instead propagates its current object-valued `player` runtime slot (`src/execute.cc:765-770`). Audit these three channels separately rather than treating them as interchangeable identity checks.
- The unlogged login task permits `do_login_command` to switch the connection with `switch_player()` before it returns; otherwise it attaches the connection only when the returned value is an object with the user flag (`src/tasks.cc:913-958`). The builtin itself requires wizard `progr`, validates the old connection and new user object, and performs the switch (`src/tasks.cc:2957-3011`).
- For the reset guard's evaluation: `is_true()` returns false by default for types without an explicit case, including object values; `OP_NOT` pushes integer `!is_true(arg)`, while `OP_IN` returns `ismember(lhs, rhs, 0)` for a list (`src/utils.cc:381-399`, `src/execute.cc:1383-1407`, `src/execute.cc:1551-1559`). Membership uses `equality()`, which returns false for integer/object pairs (`src/collection.cc:46-57`, `src/utils.cc:458-511`). The actual Mongoose guard and operands are analyzed below.
- `set_task_perms(oid)` changes `RUN_ACTIV.progr`, explicitly the top activation. A non-wizard can only set it to the current `progr`; a wizard can choose another object (`src/execute.cc:3695-3707`). `task_perms()` reads the current activation's `progr`; `caller_perms()` reads the previous activation's `progr`, or `#-1` at the root (`src/execute.cc:3710-3730`).
- `eval()` requires `is_programmer(progr)` before compiling (`src/verbs.cc:631-670`). `set_verb_code()` requires both a programmer flag and verb write permission (`src/verbs.cc:532-577`). Therefore becoming programmer is a meaningful escalation boundary even without wizard.
- `set_player_flag()` is wizard-only (`src/objects.cc:1011-1033`). `switch_player()` is also wizard-only and then validates the old connection and new player object (`src/tasks.cc:2954-3011`).
- The unlogged login task invokes `do_login_command` on `tq->handler`; if the connection is still unlogged and the result is an object with the user flag, the server assigns that object to `tq->player` and completes connection migration (`src/tasks.cc:877-958`). Mongoose's `#0:do_login_command` → `#10:welcome` → `#1414:login` source chain has now been inspected; see the snapshot-consistency caveat below.
- Protected builtin dispatch attempts `#0:bf_<name>` when the C++ `caller()` helper is not the system object; that helper returns `RUN_ACTIV._this`, not the MOO `caller` value or `caller_perms()` (`src/execute.cc:3193-3197`, `src/functions.cc:201-287`). If the wrapper call does not proceed, a non-wizard gets `E_PERM`, while a wizard can fall through to the C++ builtin. This resolves the earlier uncertainty about the YAML's `this` wording.
- Ordinary property assignment checks `db_property_allows(..., PF_WRITE)`. Built-in `.owner`, `.programmer`, and `.wizard` writes require wizard authority; `.name` has additional restrictions for user objects; `.location`, `.last_move`, and `.contents` assignments return `E_PERM` (`src/execute.cc:1959-2078`). These are direct VM gates, separate from the property-metadata builtins in `src/property.cc`.
- Existing conformance coverage includes direct non-wizard denial for `switch_player`, direct builtin wizard/programmer property writes, and protected-builtin redirection. The `switch_player` file explicitly says full active-connection behavior is not covered (`moo-conformance-tests/src/moo_conformance/_tests/builtins/switch_player.yaml:97-111`). This is useful baseline coverage, not an escalation-test suite.
- The current `scripts/fetch-mongoose.ps1` downloads `mongoose.db.new`, creates/downloads a consistent backup of `sound.sqlite`, and downloads `executables/tz` (`scripts/fetch-mongoose.ps1:9-43`). It does not inventory or fetch the other SQLite DBs/sidecars Q described, so it is not by itself a complete Mongoose replica workflow.
