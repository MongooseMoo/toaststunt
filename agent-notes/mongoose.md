## Initial source-backed authority map

This is an incomplete map of the current `mongoose` worktree, not a set of vulnerabilities or a complete permission proof.

- Object privilege/state flags are bit positions in `db_object_flag`: user, programmer, wizard, read, write, fertile, and additional anonymous/lifecycle flags (`src/include/db.h:252-279`). `is_wizard`, `is_programmer`, and `is_user` test validity plus the corresponding flag (`src/db_objects.cc:1315-1331`).
- The shared object permission helper allows an operation when the running programmer is a wizard, owns the object, or the object has the requested flag (`src/db_objects.cc:1307-1313`; contract in `src/include/db.h:289-296`). Individual builtins add their own checks, so this helper is not the whole policy.
- Programmed verb lookup requires the verb's x bit (`src/db_verbs.cc:229-237`, `src/db_verbs.cc:485-545`; contract at `src/include/db.h:581-589`). Parsed command lookup matches name and argument specifications without checking that bit (`src/db_verbs.cc:304-345`), and command execution then runs as the matched verb's owner (`src/tasks.cc:751-767`, `src/tasks.cc:811-856`, `src/execute.cc:3340-3372`). Therefore command verbs and callable verbs have different exposure rules; x-less wizard-owned command verbs remain in scope.
- Every successful `call_verb2()` activation takes its `progr` from the called verb's owner, not from the connected player or the caller (`src/execute.cc:663-740`). Command tasks likewise start with `RUN_ACTIV.progr = db_verb_owner(vh)` (`src/execute.cc:3340-3372`). Server-program tasks accept an explicit `progr` (`src/execute.cc:3291-3337`; ordinary server tasks pass the verb owner at `src/tasks.cc:1846-1861`). This makes verb ownership and callable wizard-owned verbs central to the audit.
- Nested calls set MOO `caller` from the previous activation's `this`; this is distinct from `caller_perms()`, which reads the previous activation's `progr` (`src/execute.cc:752-754`, `src/execute.cc:3721-3730`). The new activation normally inherits the previous activation's `player`; a wizard-permission caller instead propagates its current object-valued `player` runtime slot (`src/execute.cc:765-770`). Audit these three channels separately rather than treating them as interchangeable identity checks.
- The unlogged login task permits `do_login_command` to switch the connection with `switch_player()` before it returns; otherwise it attaches the connection only when the returned value is an object with the user flag (`src/tasks.cc:913-958`). The builtin itself requires wizard `progr`, validates the old connection and new user object, and performs the switch (`src/tasks.cc:2957-3011`).
- For the reset guard's evaluation: `is_true()` returns false by default for types without an explicit case, including object values; `OP_NOT` pushes integer `!is_true(arg)`, while `OP_IN` returns `ismember(lhs, rhs, 0)` for a list (`src/utils.cc:381-399`, `src/execute.cc:1383-1407`, `src/execute.cc:1551-1559`). Membership uses `equality()`, which returns false for integer/object pairs (`src/collection.cc:46-57`, `src/utils.cc:458-511`). The actual Mongoose guard and operands are analyzed below.
- `set_task_perms(oid)` changes `RUN_ACTIV.progr`, explicitly the top activation. A non-wizard can only set it to the current `progr`; a wizard can choose another object (`src/execute.cc:3695-3707`). `task_perms()` reads the current activation's `progr`; `caller_perms()` reads the previous activation's `progr`, or `#-1` at the root (`src/execute.cc:3710-3730`).
- `eval()` requires `is_programmer(progr)` before compiling (`src/verbs.cc:631-670`). `set_verb_code()` requires both a programmer flag and verb write permission (`src/verbs.cc:532-577`). Therefore becoming programmer is a meaningful escalation boundary even without wizard.
- `set_player_flag()` is wizard-only (`src/objects.cc:1011-1033`). `switch_player()` is also wizard-only and then validates the old connection and new player object (`src/tasks.cc:2954-3011`).
- The unlogged login task invokes `do_login_command` on `tq->handler`; if the connection is still unlogged and the result is an object with the user flag, the server assigns that object to `tq->player` and completes connection migration (`src/tasks.cc:877-958`). Mongoose's `#0:do_login_command` → `#10:welcome` → `#1414:login` source chain has now been inspected; see the snapshot-consistency caveat below.
- Protected builtin dispatch attempts `#0:bf_<name>` when the C++ `caller()` helper is not the system object; that helper returns `RUN_ACTIV._this`, not the MOO `caller` value or `caller_perms()` (`src/execute.cc:3193-3197`, `src/functions.cc:201-287`). If the wrapper call does not proceed, a non-wizard gets `E_PERM`, while a wizard can fall through to the C++ builtin. This resolves the earlier uncertainty about the YAML's `this` wording.
- Ordinary property assignment checks `db_property_allows(..., PF_WRITE)`. Built-in `.owner`, `.programmer`, and `.wizard` writes require wizard authority; `.name` has additional restrictions for user objects; `.location`, `.last_move`, and `.contents` assignments return `E_PERM` (`src/execute.cc:1959-2078`). These are direct VM gates, separate from the property-metadata builtins in `src/property.cc`.
- Existing conformance coverage includes direct non-wizard denial for `switch_player`, direct builtin wizard/programmer property writes, and protected-builtin redirection. The `switch_player` file explicitly says full active-connection behavior is not covered (`moo-conformance-tests/src/moo_conformance/_tests/builtins/switch_player.yaml:97-111`). This is useful baseline coverage, not an escalation-test suite.
- The current `scripts/fetch-mongoose.ps1` downloads `mongoose.db.new`, creates/downloads a consistent backup of `sound.sqlite`, and downloads `executables/tz` (`scripts/fetch-mongoose.ps1:9-43`). It does not inventory or fetch the other SQLite DBs/sidecars Q described, so it is not by itself a complete Mongoose replica workflow.

## Mongoose DB findings from the identified fixture

### Account reset: verified guard defect, no untrusted caller established

- `#3843:7` is `$account_manager:reset_password`, `rxd`, owned by wizard/programmer `#249`. Its guard is `if ((!caller) in {this.login, this.account_type}) raise(E_PERM, ...);`. Structured properties give `this.login = #1414` and `this.account_type = #3842`. For an object/waif caller, the C++ semantics above make `!caller` integer `1`; integer `1` cannot equal either listed object. The guard therefore does not reject those callers.
- `#3842:5` is `$account:set_password`, `rxd`, also owned by `#249`. It permits a call when `caller == $account_manager` or `$perm_utils:controls(caller_perms(), this)`. The reset verb drops its own task permissions to `caller_perms()` and then calls this setter; the setter sees `caller == #3843`, so the first condition is met. The reset verb's own caller checks are therefore security-critical.
- Static code searches found reset calls at `#1414:3` (`switch_to_player`, the account menu) and `#3842:0` (`validate_password`, after `argon2_verify(this.temp_password, password)`), plus the unrelated `reset_password_msg` property reference. The menu is reached after account authentication or GMCP/OAuth flows; the temporary-password path requires the emailed temporary password. No unlogged or non-wizard direct caller has been found. Dynamic invocation has not been ruled out, so this is a verified defective guard but **not** a demonstrated account-takeover path.
- `#3843:8` (`forgot_password`) requires `caller == $account_login` or wizard caller permissions, generates a temporary password, hashes it, and emails it. No password or email property values were inspected.

### Login and account-selection paths

- `#0:do_login_command` (owner `#2`) dispatches through `$login`; `#10:1` (`welcome`, owner `#2`) calls `$account_login:login()`; `#1414:0` (`login`, owner `#249`) handles account/password/guest/OAuth login. `#1414:3` presents character/account actions after authentication. `#3842:4` (`login_as_player`) requires `caller == this` or wizard caller permissions, verifies membership in `this.players`, and calls `switch_player()`.
- `#1414:0` begins with three quoted string-literal statements: `"if (caller != $sysobj)";`, `"raise(e_perm);";`, and `"endif";`. They are no-ops, so this login verb has no effective caller guard. The disposable guest probe reached its prompt and completed login, consistent with that source. An earlier assistant prediction of `E_PERM` came from misreading those quoted lines as executable code; there is no snapshot inconsistency. Post-run inspection confirmed `#0.sysobj = #0`, `#0.account_login = #1414`, and the same quoted source.
- `#1414:1` (`register`) has a caller condition followed by the string literal `"raise(e_perm);";`, not an executable raise. `#3843:2` (`create_account`) similarly has a string-literal raise for an unavailable username. The normal register flow prechecks username availability, but concurrent registrations have not been tested. Static `create_account` callers are registration, wizard-created players, and migration; `#3843:4` (`migrate_from_login`) has no static callers. `#57:13` (`@make-player`) explicitly requires a wizard and no callers before invoking the wizard-guarded `#24:23`. These are logic defects/leads, not currently demonstrated privilege escalation.
- OAuth (`#16214`) uses a 32-byte random state/nonce, binds its six-digit completion code to the originating connection, limits claim attempts, validates provider/state, and checks OIDC issuer, audience, expiry, and nonce. Existing accounts are linked only when the external email is marked verified. `#3843:19` has a separate OAuth account-creation path and does not use the defective duplicate guard in `create_account`. No guest-to-account/wizard bypass was found. Hardening observation only: `_decode_jwt_payload` checks `alg == "RS256"` and claims but does not verify a JWT signature; the inspected flow obtains the token from the provider's code-exchange endpoint, so this alone is not reported as an exploit.
- `#410:52` is `@su`, an x-less parsed command owned by wizard `#2259`, and calls `$account_login:switch_to_player(this.account)`. `switch_to_player` accepts wizard caller permissions, so `@su` relies on the integrity of the player's `.account` reference. Structured metadata shows `.account` is defined on `#6` with only `r` permission and owner `#249`; ordinary players therefore cannot directly rewrite it through normal assignment (`src/execute.cc:2006-2010`, `src/db_properties.cc:767-772`). Executable wizard-owned `.account` writers are limited to the account creation/migration paths found by `moodb grep`; those callers still need review.
- `#4583` is `$gmcp_autologin`. `send_token` requires `caller == this` and creates an identifier with `string_hash(tostr(time(), random_bytes(16)), "SHA512")`; `#4579` stores the account and a 90-day expiry. GMCP routing is `#3838:handle_message` → `#2729:route_message` → `#1695:route_message`, which prefixes the parsed subaddress with `handle_`; on `#4583` this exposes `handle_login`, not arbitrary verbs. The connection is assigned from `player`. `handle_login` checks token presence, account validity, and expiry before account login/switch methods. The token is a bearer credential usable from a new connection; no token or connection-binding bypass was found in the inspected code. No token values were read.
- The Ops/Away identity chain was also traced: `#5289:handle_request` issues a five-minute Client.WebPush token for `player` itself; `#68999:token` validates it with `#5289:validate_request` and mints a 30-day Away token for that same player; `#68987:token_player` hashes the presented token and checks expiry and player validity. Token generation uses `random_bytes(16)` for WebPush/GMCP and `random_bytes(32)` for Away. The C++ builtin uses the Sosemanuk PRNG (`src/numbers.cc:1152-1167`), initialized with a 32-byte key read from `RANDOM_DEVICE` outside `TEST` builds (`src/server.cc:1337-1377`). No request-controlled wizard identity was found in this chain.

- The unlogged `$login:parse_command` path admits only x-enabled `any none any` verbs. On `#10`, those are help/welcome/who/quit/uptime/version/request/REGISTER/newlogin/guest; legacy connect/create/login variants lack x and are not admitted. `request_enabled = 0`, and `$player_class` has `programmer = 0` and `wizard = 0`. `#10:59` (`guest`) returns a deferred guest object, consistent with the successful probe.
- SunNET is active and `#10:47` (`REGISTER`) returns a remote-link object after checking its `net_password`. The existing `SunNET_*` objects returned by `moodb players` are all flagged only `player`, not programmer or wizard. The creation path sets the player flag but not privilege flags (`#2664:14`); new objects start with flags `0`, and C++ wizard/programmer checks use the object's own flags (`src/db_objects.cc:269-272`, `src/db_objects.cc:1315-1330`). No SunNET authentication bypass was found, and no password values were read.

### Programmer/wizard and agent paths reviewed

- `#24:0` (`$wiz_utils:set_programmer`) requires `caller_perms().wizard`. Its only static caller is `#57:3` (`$old_wiz:@programmer`), which first does `set_task_perms(player)`, so the downstream check receives the connected player's permissions. A non-wizard is denied. `#57:26` (`@deprogrammer`) also explicitly requires `player == this && player.wizard` after dropping permissions.
- `#3842:6` (`create_temp_player`) copies `parent_player.programmer` and `.wizard` to the new player, but requires `caller == this` or wizard caller permissions. `#21244:0` (`@launch-agent`) drops to `player` before calling it, so an ordinary player fails that guard; `#21244:16` (`@resume-agent`) explicitly requires a wizard. `#11236:32` (`$issues:_launch`) requires its own wizard caller and drops to the dispatcher's permissions.
- `#138751` (`Ops API`) has `_who` restricted to a valid wizard returned by `$away:bearer_player(request)` and listed in `$away.allow_privileged`; that list is `{#13505}` in this fixture. Its `eval` method drops task permissions to that authenticated wizard; `command` and `launch` create temporary players for that identity. The Away token issuance chain described above does not let the requester select another player. No ordinary-player path was found here.
- The queried `#0.protect_set_task_perms`, `protect_switch_player`, `protect_set_player_flag`, `protect_eval`, and `protect_set_verb_code` properties are absent in this fixture. `server_flag_option()` returns the supplied default when the property is absent (`src/server.cc:1410-1417`), and the builtin loader supplies `0` (`src/functions.cc:513-521`), so these five builtins do not use `#0` protected redirection here. `verbs #0` also listed no `bf_*` wrappers.
### Command and inline-evaluation review

- `#0:do_command` first calls `#214:do_command`. The inline parser requires `player.programmer` before evaluating `<; ... ;>` substitutions. Its `#214:eval` helper additionally requires `caller == this` and a root `#0` caller. No ordinary-player inline-eval path was found.
- `#6:my_huh` dispatches feature commands after setting task permissions to the player when authorized (or `$no_one` when not). Thus `#3885:@database-shell` evaluates its database-owner/wizard check against the actual player, not the feature's wizard owner. Default ordinary/guest feature lists were inspected; their high-impact searches found no direct `eval` or `set_verb_code` path. `#279:@xeval-d` sets `$no_one` permissions.
- Global parsed-command searches covered `force_input`, `eval`, `set_verb_code`, player flags, `.wizard`/`.programmer`, `set_task_perms`, and verb/property/parent/owner mutation. No parsed-command `eval` or `set_verb_code` call was owned by a programmer-only player. `#769:@ansi-setup` requires both `player.wizard` and wizard caller permissions; `#2236:install` requires `player.wizard`. The task-permission sweep found no fixed wizard assignment on an ordinary-player command. Other mutation candidates were wizard/builder-scoped, alias/game operations, or lacked a demonstrated ordinary-player caller.
- No guest/ordinary-player-to-programmer/wizard escalation has been reproduced. All DB findings above are static analysis of the identified snapshot except for the explicitly recorded disposable guest/MQTT run.

## Next step

1. Close the reset guard's reachability question, including possible dynamic invocation. Do not report it as an account-takeover vulnerability without a real untrusted caller; if a justified test remains, use a disposable account in an outbound-disabled fixture.
2. Before any further launch, inventory saved tasks, outbound startup services, required SQLite databases, executables, and other sidecars. Use uppercase `-O` and a private port for every security probe. 4. Keep the reset guard as a verified defect with unproven reachability. No candidate escalation has been reproduced. Do not implement fixes or new test code without Q's explicit go-ahead.
